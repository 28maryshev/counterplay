# Проверки

Не юнит-тесты, а замеры на живых данных: собирают цифры и выносят вердикт по
порогам. Возвращают 0, если всё в порядке, и 1, если какая-то проверка не прошла.

## PoolBias — перекос пула в оценках

Отвечает на вопрос «не задираются ли пул и дуо перед обычным подбором».

```
dotnet run --project tests/PoolBias/PoolBias.csproj
```

Берёт боевую базу приложения (`%APPDATA%\Counterplay\data.db`), а если в ней нет
таблиц матчапов и синергии — срез из репозитория (`data-slice.db`; в срезе их
нет, и мерить на нём нечего). Гоняет по 40 случайных, но воспроизводимых
драфтов на каждую роль.

Что меряет:

- прибавку к оценке, которую даёт попадание чемпиона в активный пул;
- ту же прибавку для дуо-пула (должна совпадать);
- на каком фоне она получается — разрыв между соседями в топ-10 и разброс
  оценок с 1-го по 6-е место;
- сдвиг по местам и долю случаев, когда чемпион залетает в топ-6 только из-за
  прибавки;
- совпадает ли оценка карточки пула с оценкой того же чемпиона в общем списке
  (карточки считаются по `only`-списку, где нет порога кандидатов);
- не складывается ли пул с наигранностью (должен браться максимум, не сумма);
- насколько пул из сильных, средних и слабых чемпионов отстаёт от общего №1.

Пулы подставляются **в памяти**: `Persist` не вызывается, `pools.json`
пользователя не трогается — проверка это подтверждает отдельно.

Важно при правках: базу отсчёта (режим «Обычный», пул выключен) надо задавать
явно. Первая версия проверки этого не делала и мерила от реального пула
пользователя — выходило, будто у чемпионов вне пула отнимают очки.

## DbSwap — подмена базы, скачанной фоном

```
dotnet run --project tests/DbSwap/DbSwap.csproj
```

База обновляется, пока программа работает: скачанное ложится рядом
(`data.db.new`) и подменяет рабочую в перерыве между драфтами. Держится это на
двух вещах, и обе тут проверяются.

**Замок на файле.** Под открытым соединением подменить базу нельзя — это и есть
причина, по которой подмена ждёт конца драфта. Хуже того, одного `Dispose` мало:
`Microsoft.Data.Sqlite` держит закрытые соединения в пуле, и файл остаётся
открытым. Поэтому `ApplySwap` чистит пул явно. Уберите ту строку — проверка
падает, а в жизни скачанная база не применилась бы никогда и качалась бы заново
каждый запуск.

**Сама подмена** гоняется на боевых именах файлов, но во временной папке:
`DataDb.DirOverride` существует только ради этого. Своя база игрока не годится —
её держит открытой запущенная программа, да и портить её нельзя.

**Полоса внизу сайдбара** проверяется по последствию, а не по картинке: фоновая
полоса НЕ уводит окно на экран загрузки (ширина драфта не меняется), а полоса
первого запуска — уводит, как и раньше.

## PatchPull — база тянется на новый патч

```
dotnet run --project tests/PatchPull/PatchPull.csproj
```

Программа живёт в трее сутками, а версия базы сверялась только на запуске: кто
не перезагружается, сидел на базе прошлого патча. Теперь сверка идёт раз в три
часа, вместе со сторожем патчей.

Ключевое решение — **сверяться по патчу, а не по версии файла**. Пайплайн
перевыкладывает базу почти каждый день, добирая матчи, и версия меняется вместе
с ней. Гнаться за версией значило бы сливать человеку по сотне с лишним
мегабайт в сутки; внутри патча данных на диске достаточно.

Проверка поднимает свой `HttpListener` и гоняет через него весь путь:
`DataDb.SourceOverride` и `DirOverride` существуют ради этого. Сервер считает
ЛЮБОЕ обращение за базой, включая запасной путь без сжатия, — иначе промах
второй сверки остаётся невидимым.

Что ловится при откате: уберите сверку по патчу — падает шаг 2 («внутри патча
база не качается»); уберите замок на одновременные закачки — падает шаг 5, две
сверки лезут за базой дважды и вторая спотыкается о занятый `.tmp`.

## SideHints — три иконки под портретом

```
dotnet run --project tests/SideHints/SideHints.csproj
```

Под портретом врага стоят его контры, под портретом союзника — с кем мне с ним
играть. Владелец: «их всегда должно быть только 3, и работать они должны от
твоей роли у союзников, а контры у врагов — относительно их роли».

Под Векс на миде стояла одна иконка. Дело было не в нехватке данных: парные
таблицы не знают, кто роль правда играет, и в кандидаты лезли Фиддлстикс-мид на
восемнадцати играх и Сивир-мид на пятнадцати. Порог такие отсекал, а вместе с
ними и всё остальное.

Проверка считает состав ролей **сама**, прямо из `base_wr`, и по своей планке
(0,4% и 120 игр — мягче кодовых 0,5% и 150). Иначе она повторяла бы число из
движка и молчала бы вместе с ним.

Что ловится при откате: уберите фильтр роли в контрах — в подсказки возвращаются
187 чужих для роли чемпионов; уберите добор до трёх — 49 чемпионов остаются с
одной-двумя иконками; уберите ровные пары — Джинкс снова показывает две (в её
роли нет НИ ОДНОГО победного матчапа); уберите фильтр роли в синергии — 1193
чужих напарника; забудьте роль союзника — у флекс-пиков напарники перестают
зависеть от линии.

## Archetype — треугольник архетипов

```
dotnet run --project tests/Archetype/Archetype.csproj
```

Владелец про Пайка: «он должен быть dive чемпионом, разве нет?». Оказалось, что
да: Пайк был оттегирован как хук-ТАНК, в один ряд с Трешем и Блицкранком, и
полкита не было записано вовсе — невидимость на W, рывок на E, добивающий ульт.

Дыра в рукописных тегах ничем себя не выдаёт: чемпион просто оказывается не в
той трети треугольника, а от неё зависят и подсказка по стилю, и «против их
стиля» в оценке. Поэтому проверка не про Пайка, а про КЛАСС ошибки: кого сам
Riot считает убийцей, тот не может остаться вовсе без признаков дайва.

Два списка исключений держатся отдельно. «Не дайверы по существу» — Тристана и
Твич: Riot приписал им Assassin за прыжок и невидимость, но стоять им сзади.
«Известные дыры» — Ари, Ясуо, Ёнэ: видим и пока не поправили. Проверка следит,
чтобы второй список не РОС, и печатает его на каждом прогоне.

Что ловится при откате: верните Пайку прежние три тега — падают все три пункта
(архетип, «новых дыр нет», «Пайка среди них нет»).

## Чего тут больше нет

**SlowUpdates** проверял срок ожидания для проверки обновлений на запуске. Сам
срок понадобился, только пока проверка держала старт; теперь обновления ушли с
пути запуска целиком — сайдбар показывается сразу, а версия качается и встаёт
фоном. Ждать стало нечего, `Deadline.OrNull` остался без применения, и проверка
вместе с ним убрана: код, который ничего не защищает, врёт о покрытии.
