# Сбор статистики

Сбор матчей Riot MATCH-V5 → рабочая база `data.db` → после каждого круга
сбора — публикация тонких баз для программы и бота (своё хранилище и GitHub
release `data`) и выгрузок для сайта (тир-лист, контрпики, драфт-инструмент,
руны). Программа обновляется сама по `data-version.json`.

Два способа запуска — одинаковый код, разный сценарий:

| | Где | Когда |
|---|---|---|
| **CLI** | твоя машина | разовый сбор, отладка |
| **Сервис** | сервер, 24/7 | постоянный сбор, ключ шлёшь из Discord |

## Сбор параллелится по регионам

Riot считает лимит на пару **(ключ, хост роутинга)**, а не на IP. Поэтому:

- регионы (`euw1`/`na1`/`kr`) идут **в потоках одновременно** — каждый со своим
  лимитером, прирост почти линейный;
- регионы с общим хостом MATCH-V5 (`euw1`+`eun1` → `europe`) сами встают в
  очередь этого хоста, лимит не нарушается;
- **больше инстансов не ускорят** сбор: лимит на ключе, а не на машине. Реальный
  прирост даёт только production-ключ (30 000 req/10 мин против 100 req/2 мин).

## Что происходит после круга

1. `publish_data.py` собирает тонкие базы (только таблицы движка, три последних
   патча, без пар с одной игрой) — общую и по одной на эло — и заливает их в
   своё хранилище и в GitHub release `data`. Номер версии заливается последним.
2. Демон оставляет отметку для сайта; сторож `site_watch.sh` на хосте (cron,
   каждые 5 минут) запускает `publish_site.sh`: выгрузки `export_tiers.py`,
   `export_draft.py`, `export_runes.py` уезжают на сервер сайта, сайт
   пересобирается, кэш сбрасывается.
3. `prune_db.py` чистит рабочую базу (старые патчи, давно обойдённые игроки) и
   сжимает файл — сбор в это время стоит, поэтому сжимать безопасно.

## Находки для постов

Считать по базе на самом сервере сбора нельзя: памяти мало, а рядом идёт сбор.
Поэтому расчёты живут на машине разработки:

```bash
bash ops/pull-stats.sh                 # выжимка за последние два патча → data-slice.db
python pipeline/findings.py --db data-slice.db
python pipeline/findings.py --db data-slice.db --json > findings.json
```

Пост в #meta-radar — оттуда же, но никогда сам собой:

```bash
python pipeline/findings.py --db data-slice.db --preview    # показать, что уйдёт
python pipeline/findings.py --db data-slice.db --post       # отправить от имени бота
```

Пост уходит от имени бота через `ops/post-radar.sh`: текст едет на сервер, а
токен бота остаётся там. Запасной путь — веб-хуком (`--webhook <url>`). На
экране находки по-русски, в канал уходит английский: остальные сообщения бота
там английские.

`findings.py` ищет то, что прошло порог значимости: предмет или руну стали брать
иначе, сборка обгоняет свой уровень, популярный выбор хуже менее популярного, и
самое надёжное — когда одно и то же повторилось у нескольких чемпионов разом.

Три правила расчёта расписаны в шапке самого файла, и нарушать их нельзя:
винрейт сборки мерит длину игры (сравнивать только с играми той же длины); долю
считать от РАЗОБРАННЫХ игр, а не от всех (покрытие росло от патча к патчу); порог
нужен и статистический, и по размеру эффекта. И причинность в посте не пишется:
«стали собирать — и вот что стало», а не «предмет поднял винрейт».

## CLI

```bash
py -3.12 pipeline/collect.py                       # ключ спросит сам, соберёт всё
py -3.12 pipeline/collect.py --region euw1,na1,kr  # только эти регионы
py -3.12 pipeline/collect.py --verify              # проверить разбор на одном матче
py -3.12 pipeline/publish_data.py --db <база>      # выложить базу (нужен GITHUB_TOKEN)
```

## Сервис на сервере

Ставится рядом с ботом — они делят том `control`: бот кладёт туда ключ,
коллектор его подхватывает.

```
~/counterplay-bot/        (бот)
~/counterplay-collector/  (этот каталог)
  ├── control/   ← общий с ботом: key, status, отметка для сайта
  └── data/      ← data.db и ops.db (переживают пересборку)
```

### Развернуть

```bash
# 1. Залить код (данные и control в образ не попадают — см. .dockerignore)
scp -r pipeline SERVER:counterplay-collector
scp pipeline/.env SERVER:counterplay-collector/.env     # заполнить из .env.example

# 2. ВАЖНО: засеять уже собранную базу — иначе коллектор начнёт с нуля
#    и заново перемелет то, что уже есть.
ssh SERVER 'mkdir -p counterplay-collector/data counterplay-collector/control'
scp data.db SERVER:counterplay-collector/data/data.db

# 3. Поднять
ssh SERVER 'cd counterplay-collector && docker compose build collector && docker compose up -d collector'
ssh SERVER 'docker logs -f counterplay-collector'
```

Код запекается в образ: после правки нужна пересборка (`build`), простой
`restart` поднимет старый код. Скрипты `publish_site.sh` и `site_watch.sh`
работают на самом хосте, а не в контейнере, — им пересборка не нужна.

### Работа

Все команды эфемерные (ключ не попадает в историю канала) и только для
`ADMIN_USER_IDS`:

- `/collect key value:RGAPI-…` — прислать свежий ключ, сбор стартует;
- `/collect status` — что делает коллектор сейчас;
- `/collect stop` — убрать ключ, сбор встанет после текущего матча.

Дальше всё само:

1. коллектор собирает параллельно по регионам;
2. круг пройден → база публикуется, сайт обновляется, следующий круг идёт тем же
   ключом (ключ живёт сутки, круг — часы);
3. **ключ истёк** → в Discord просьба прислать новый, собранное публикуется;
4. присылаешь новый ключ → сбор продолжается с того же места
   (матчи и игроки дедуплицируются глобально).

### Память и место

Сбор ждёт ответов Riot и почти не занимает процессор. Контейнер ограничен
450 МБ (`mem_limit`): меньше — и кэш файлов выдавливал процесс в своп, а
публикация растягивалась с минут до часов. Рабочая база — несколько гигабайт;
при нехватке места сбор сам останавливается, публикует собранное и ждёт, пока
место освободят.
